# Saved package evidence check

The borrower package screen previously tested private artifact paths that the status API intentionally omits. The screen and HTTP journey runner now use all six safe `readiness.packageFiles` flags, while still requiring a successful bundle. The screen retains assumption freshness and release checks. No storage paths or internal memo are added to the borrower response.

Current processing capacity is checked on idle status reads and again before starting a preparation workflow. Existing worker checks and atomic AI gateway reservations remain authoritative under concurrency. Unavailable or unreadable capacity prevents admission; this change never changes caps or usage ledgers.

`POST borrower-actions/check-package` is an authenticated, deal-scoped, rate-limited, explicit no-AI diagnostic. It requires completed borrower inputs and saved validation/research prerequisites. It checks the actual saved financing lines against canonical lines, computes a fresh in-memory financial snapshot with the existing factory calculators, and runs the existing credit-memo and feasibility preflight. No preparation job, research, model call, snapshot write, artifact, score, signature, or release is created. Input hashes before and after prevent a passing result across concurrent edits. Only safe status messages and allowlisted recovery guidance leave the server.

Missing preparation outputs or unsynchronized financing lines produce **not checked**, not a pass. The check cannot bootstrap paid research or reconcile a lender-reviewed financing schedule. The normal preparation transaction remains responsible for synchronization and validation. A passing diagnostic only covers current saved evidence; generated prose, rendered package contents, final certification, identity, signatures, and bank acceptance still need separate verification. The UI clears the diagnostic when inputs change.

The HTTP journey now validates prepared-artifact status without requiring private paths. It checks the internal memo stays unavailable to borrowers. Before bank selection it verifies the expected download lock and reports an incomplete journey with exit code 2. Only an authorized download whose PDF/XLSX/ZIP contents pass validation can produce `package_verified`.

Verification covers API admission with unavailable capacity, a capacity race after admission, read-only preview behavior and tenant mismatch, stale financing lines, concurrent input changes, safe failure output, locked/released/missing/stale package UI, and HTTP release-lock leakage. The broader no-network regression suite also exercises the real memo, feasibility, projection, validation, and SQL policies. Desktop/mobile component tests use isolated API fixtures and do not claim live vendor verification.
